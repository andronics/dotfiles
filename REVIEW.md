# dotlib review — 2026-08-27

**Status: implemented.** All items in the [decisions table](#proposed-decisions-keep--merge--discard) and the recommendation list have been applied to the working tree (not committed). Left as a record of what was found and why, not a pending plan.

Scope: the 32 modules under `shell/.local/share/dotlib/` (~31,500 lines) plus how they're actually consumed by `~/.local/bin/` wrappers and the `desktop/` scripts. This follows the earlier cleanup pass (deleted `_ui`, `_patterns`, `_tour`, `_args`/`_async`/`_rules`/`_server`, `_template`/`_schema`/`_actions`/`_plugins`, `_docker`/`_acpi`/`_git`/`_dryrun`/`_http`, `_ai_core`/`_ai_claude`/`_vpn`/`_wifi`/`_crypto` — ~20 modules, ~8,900+ lines of zero-consumer code). That pass proved dead-module deletion works. This review asks whether what's *left* still has the same disease at a finer grain.

## Bottom line

**Refactor around a rewrite of the "infrastructure" layer, don't try to trim your way out of this.** The remaining 32 modules aren't bloated because nobody deleted the unused ones yet — they're bloated because the same concern (XDG paths, validation, string casing, event pub/sub, self-testing) was independently reimplemented at multiple layers, and *all* the copies are still being called from somewhere, so file-level "is this dead" deletion won't touch it. The fix has to be architectural: pick one implementation per concern and delete the others, not just prune unreferenced files.

## 1. The same concern, reimplemented at multiple layers, both copies alive

This is the main finding. It's not hypothetical duplication — I checked real call sites across the whole repo, not just dotlib itself.

- **XDG paths**: `_common` has its own `common-xdg-data-home`/`common-xdg-config-home`/etc. (`_common:1-6`-ish), *and* there's a dedicated `_xdg` module (657 lines) with `xdg-data-dir`/`xdg-config-dir`/etc. Both APIs are live: `common-xdg-*` has 31 call sites, `xdg-*` has 47. Different modules pick different one depending on who wrote them. Deeper than that: `_common` also had a second, self-built convenience layer on top of its own bare-home functions — `common-lib-data-dir`/`-cache-dir`/`-state-dir`/`-config-dir`, which just append a fixed `/lib` segment — with **9 more external callers** (`_events`, `_cava`, `_process`, `_bsp`, `_rclone`, `_config`, `_bluetooth`, `_cache`) duplicating exactly what `xdg-*-dir <app>` already does, one layer deeper than the first pass of this review caught.
- **Validation**: `_common` has `common-validate-required`/`common-validate-file`/`common-validate-directory`/`common-validate-numeric`/`common-validate-enum`, used across 13 files (`_player`, `_screenshot`, `_cache`, `_config`, `_audio`, `_string`, `_bluetooth`, `_events`, `_rclone`, `_bsp`, `_lifecycle`, plus itself). Meanwhile `_validation` (938 lines) implements a much more thorough `validate-type-*`/`validate-constraint-*` system — and it has **zero callers anywhere outside itself**. On inspection `_validation` is the better implementation (composable type+constraint checks, routes errors through `_validation-log-error` instead of raw `echo`, and its `validate-type-enum` already calls `common-validate-required` internally, so the dependency direction for a merge is already correct). `_network` stays parked for its future project, but `_validation` shouldn't — see [decisions](#proposed-decisions-keep--merge--discard) below.
- **String casing/trimming**: `_common` defines `common-trim`, `common-to-lower`, `common-to-upper` — used nowhere outside `_common` itself. `_string` (931 lines) defines `string-trim`, `string-lowercase`, `string-uppercase` and is what `_player` actually calls. The `_common` versions are pure dead weight sitting next to the real thing.
- **Event systems**: `_events` (1,093 lines, 37 functions) is a full pub/sub bus — `events-on`/`events-emit`/`events-emit-async`/history/queueing/logging. `_lifecycle` (2,580 lines) wraps it in its own facade (`lifecycle-event`, `lifecycle-event-trigger`, `lifecycle-event-once`, `_lifecycle_emit`) — correction from an earlier pass of this review: this isn't a second independent engine, `_lifecycle_emit` just calls `events-emit` when `_events` is loaded. But `_lifecycle` unconditionally sources `_events`, so its "fall back to an internal dispatcher if `_events` isn't available" branch (`_lifecycle_internal_event_dispatch`) never runs, and none of the four `lifecycle-*` functions with real callers touch the event facade at all — it's dead weight with no caller, not a competing implementation.
- **Self-testing**: 23 of 32 modules define their own `<prefix>-self-test()` that hand-rolls a `tests_passed`/`tests_failed` counter loop (`_dispatcher`, `_lifecycle`, `_audio`, `_bluetooth`, `_bsp`, `_cache`, `_cava`, `_config`, `_events`, `_format`, `_jq`, `_network`, `_notify`, `_process`, `_rclone`, `_rofi`, `_singleton`, `_string`, `_systemd`, `_xdg`, `_xidlehook`, `_common` itself, `_test`...). There's a dedicated `_test` module (818 lines) for exactly this job, and it is **not used by a single one of them**.

## 2. Most of the library has no real caller

Only 7 wrappers exist in `~/.local/bin/`: `audio`, `bt`, `player`, `remote`, plus desktop's `bsp`, `lockscreen`, `screenshot`. Walking the real dependency graph from those entry points reaches 29 of the 32 modules (everything except `_network`, `_test`, `_validation` — the first two intentionally parked, the third effectively unused). So it's not that two-thirds of the library is unreachable; it's the opposite problem — almost everything *is* wired up, which is exactly why duplicate implementations coexist instead of one winning. `_lifecycle` is the extreme case: 94 functions / 2,580 lines covering signal traps, a cleanup dependency graph with cycle detection, process-group management, job/PID tracking, temp-file/dir tracking, service tracking, an execution state machine (`start`/`complete`/`fail`/`skip`/`history`), and save/load/resume checkpointing — for a personal CLI toolset whose actual jobs are "toggle mute," "connect a bluetooth device," and "mount a Drive folder." The dotlib README itself says most modules are "aspirational until claimed by a wrapper" — that's true, but the ones that *have* been claimed are still carrying this much unused surface area internally.

Rough confirmation: 1,224 functions are defined across dotlib; a conservative same-name grep across the whole repo puts at least 72 of them at zero call sites outside their own definition (this undercounts — it's a fixed-string search, so it's a floor, not the true number).

Uniform "Part of the dotfiles library v2.0" / "Layer 1/2/3" headers appear in 30 of 32 files with consistent version stamps (`_bluetooth`, `_audio`, `_cava` at "v3.0" deps, etc.) — cosmetic, but it's a tell that this was generated in large uniform batches rather than grown organically function-by-function, which matches the duplication pattern above (batch-generated modules don't know what a sibling batch already built).

## 3. A second, unrelated ecosystem sitting next to dotlib

Most of `desktop/.local/bin/` doesn't touch dotlib at all: `bsp-flag`, `bsp-floating-borders`, `bsp-ventilate`, `terminal`, `sxhkd-bindings`, `nemo-rename`, `wifi-monitor`, `x11-events`, `x11-info`, `x11-monitor`, `polybar-reload` (~700 lines, 11 of 13 desktop scripts) have no `${DOTLIB}` reference whatsoever and hand-roll their own logging/state instead of reusing `_log`/`_singleton`/`_xdg`.

Three of these (`bsp-flag`, `bsp-floating-borders`, `bsp-ventilate` — currently untracked/WIP per git status) use a different, older convention entirely: `source $(which _log)`, `source $(which _singleton)`, `source $(which _onexit)`, `source $(which _func)`. I checked this empirically rather than just reading it: **`DOTLIB` is never added to `$PATH`** (`shell/.config/zsh/.zshenv.d/10-dotlib` only exports the `$DOTLIB` variable), so `which _log`/`which _singleton` resolve to nothing right now. And `_func`/`_onexit` don't exist anywhere in the repo — they were presumably casualties of an earlier module-deletion pass. So these three new scripts would fail immediately on `source $(which _func)` if run today. They aren't wired into `bsprc`/`sxhkdrc` yet, so this isn't an active production break, but it shows that even brand-new code being added to this repo right now doesn't have one clear pattern to follow — there's dotlib's `${DOTLIB}/_module` convention, and there's this dead `which _module`-on-PATH convention, coexisting.

## Proposed decisions: keep / merge / discard

Bias throughout: prefer several small single-purpose files over one big grab-bag, and prefer functions that earn their existence via a real caller over pre-built speculative surface.

| Concern | Keep | Discard | Note |
|---|---|---|---|
| XDG paths | `_xdg` (already a clean, focused module) | `_common`'s `common-xdg-*` and `common-lib-*-dir` | `_xdg` couldn't just take over `common-xdg-*-home` as-is — `xdg-*-dir` called it internally, and `_common` is a foundational dependency `_xdg` itself requires, so `_common` depending back on `_xdg` would invert the hierarchy. Fixed by inlining the five trivial `${XDG_*_HOME:-default}` one-liners directly into `_xdg` (no dependency needed for that) and deleting `common-xdg-*` from `_common` outright. `common-lib-*-dir`'s 9 external callers were migrated to `xdg-*-dir <app>` directly (dropping the pointless `/lib` segment). Of `_common`'s own six `common-lib-*` functions, five turned out to have no real caller at all once the external migration was done — `data-dir`/`state-dir`/`config-dir` were dead outside a `common-lib-ensure-dirs` that itself had zero callers anywhere, and `docs-dir`/`template-dir` pointed at `~/.local/share/lib/{docs,templates}` directories that never existed on disk (referenced only by two dead `cat $(common-lib-docs-dir)/...` lines in `_config`/`_cache` help text and by `_common`'s own self-test). Deleted all five, initially keeping only `common-lib-cache-dir` since it backed `_COMMON_CMD_CACHE_FILE` — `_common`'s file-based cache of `command -v` results, used by `common-command-exists` (18 external callers). That cache had no invalidation path other than a `common-command-cache-clear` function nothing ever called: once a command was checked and cached as missing (or present), `common-command-exists` would keep returning the stale answer forever, even after the binary was installed/removed — a real, previously-hit bug, not just a style issue. Deleted the whole caching layer (`_common-init-cmd-cache`, `_common-cache-command`, `common-command-cache-clear`, `_COMMON_CMD_CACHE_FILE`) and reimplemented `common-command-exists` as a direct `command -v` check — same name and contract for all 18 callers, just always correct. That left `common-lib-cache-dir` with no real caller either, so it's gone too; `_common` now has no XDG/cache-path awareness of any kind. One exception: `_events` gets the same inlined one-liner instead of sourcing `_xdg`, because `_xdg` optionally sources `_lifecycle`, which optionally sources `_events` — making `_events` require `_xdg` would create a real (if currently harmless, guard-protected) load cycle for the sake of one path. Verified no real data existed at the old `~/.config/lib/*` etc. paths before dropping them — all empty or belonged to already-deleted modules. |
| String casing | `_string` | `_common`'s `common-trim`/`common-to-lower`/`common-to-upper` | Zero external callers — straight delete, no migration. |
| Validation | `_validation`'s `validate-type-*`/`validate-constraint-*` | `_common`'s `common-validate-*` | Reversed from an earlier pass of this review, which deferred to "`_validation` is parked for a future project" as a reason not to touch it — that shouldn't have blocked a technical call. `_validation` is the better design (composable type+constraint checks, consistent error routing) and already depends on `_common`, so the merge direction is correct. Two real gaps to close first: (1) `common-validate-file`/`-directory` also check readability and return a distinct permission-denied code — `_validation` has no `validate-constraint-readable`, needs adding (same shape as its other seven constraint functions); (2) `common-validate-enum` takes a space-separated list, `validate-type-enum` takes pipe-separated — call sites need reformatting, not just renaming. After that, migrate the 13 callers and delete `common-validate-*`. |
| Event system | `_events` | `_lifecycle`'s internal fallback dispatcher + the whole `lifecycle-event*` facade | No caller touches the facade (see correction above) — delete it, hard-depend on `_events` for the two real internal uses (signal/exit events). |
| Self-testing | inline per-module boilerplate as-is | `_test` module | 0 adoption after 23 real opportunities. The duplication here is cheap (a counter loop, not logic) — not worth retrofitting 23 files onto a shared framework. Delete the unused module. |
| `_lifecycle` | signal traps + cleanup registration + job tracking (~300 lines) | everything else | Checked real callers across every module reachable from the 7 wrappers: only **4 of 94 functions** are ever called — `lifecycle-cleanup`, `lifecycle-cleanup-add`, `lifecycle-track-job`, `lifecycle-untrack-job`. Process-group management, restart/monitor, checkpoint save/load/resume, and the execution state machine have no caller anywhere. This isn't a module to split into five — it's one appropriately-sized module (cleanup-on-exit + job tracking) buried under ~2,200 lines of unbuilt framework. Delete the framework; what's left needs no further fragmenting. |
| Desktop scripts (`bsp-flag`, `bsp-floating-borders`, `bsp-ventilate`) | — | the `source $(which _module)` convention | Point them at `${DOTLIB}/_log` and `${DOTLIB}/_singleton` directly. Don't force them (or the other 8 non-dotlib desktop scripts) onto the full `dispatcher-init`/`_dispatcher` contract — reusing small primitives like `_log`/`_singleton` is cheap; making every desktop script a dispatcher citizen would over-apply the framework to scripts that don't need subcommand routing. |

## What's actually fine — keep it

- The **wrapper contract** itself (thin `~/.local/bin/<noun>` → `dispatcher-init`/`dispatcher-execute` → `_<module>` functions) is a good pattern and the wrappers that exist (`audio`, `bt`, `player`, `remote`) follow it cleanly — all well under the 30-line budget, no business logic leakage.
- `_dispatcher` (997 lines) does one job — command routing, aliasing, help/completion generation — and is used correctly by every real wrapper. It's larger than it needs to be (30 functions, including full bash *and* zsh completion generators for a personal tool) but it's not duplicated elsewhere.
- The modules with real, singular ownership of their domain — `_audio`, `_bluetooth`/`_bt` (legitimate two-layer split: `_bluetooth` is MAC-only backend, `_bt` resolves names to MACs and adds rofi/notify UI — not duplication), `_player`, `_rclone`/`_remote` family, `_bsp` — are the actual product. They're what the rewrite should preserve behaviorally.

## Recommendation

Don't do another module-by-module "is this file dead" pass — you already did that and it's not the problem anymore. Work the [decisions table](#proposed-decisions-keep--merge--discard) above:

1. **Migrate the three `_common` duplicate clusters onto their real implementations** — `_xdg`, `_string`, and (after adding the missing readable/writable constraint and reformatting the enum call sites) `_validation` — then delete the `_common` copies. `_common` should end up holding only genuinely generic, no-natural-home utilities (command existence, retry/timeout, temp files, OS detection) once these three are out.
2. **Delete `_lifecycle`'s dead event facade** and hard-depend on `_events` for its two real internal uses.
3. **Cut `_lifecycle` down to the four functions with real callers** (`lifecycle-cleanup`, `lifecycle-cleanup-add`, `lifecycle-track-job`, `lifecycle-untrack-job`) plus the signal-trap machinery they sit on. Delete process-group management, restart/monitor, checkpointing, and the execution state machine — none have a caller.
4. **Delete `_test`** — 0 adoption after 23 real opportunities; not worth retrofitting.
5. **Fix the `bsp-flag`/`bsp-floating-borders`/`bsp-ventilate` sourcing** to use `${DOTLIB}` instead of the broken `which _module` convention, without pulling the other desktop scripts onto the full dispatcher contract.
